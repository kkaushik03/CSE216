## Abstract [15]

2. **Problem:** we do not know how accessible these interfaces are by default, or how much guidance it takes to make them accessible.

3. **Task and prompts.**

   - The three levels.
   - The prompts are zero-shot and single-turn, and share one structure.

   - Full prompts go in the appendix.
4. **Generation procedure.**
   - The Docker runner: a clean container, no local settings, a pinned image.
   - Each run gets one prompt and runs to completion without human input.
   - The runner records the model, CLI version, prompt hash, and timestamps.
5. **Automated evaluation.**
   - Tool versions: axe-core 4.14.0, Pa11y 10.0.0 with HTML_CodeSniffer WCAG2AA, Lighthouse 13.6.0, Siteimprove Alfa 0.84.3, the Nu HTML Checker 26.11.4, and Chromium 156, all in Docker. Details and the reasons for each tool are in `docs/checks.md` ("Tools" and "For the paper").
   - Three tools are independent WCAG engines: axe-core, HTML_CodeSniffer (in Pa11y), and Alfa. Lighthouse is built on axe-core. Nu checks HTML validity, not a WCAG criterion (WCAG 2.2 removed 4.1.1).
   - How views are found: the start page plus one click on each navigation item, at most 8 views, at 1280 × 800.
   - What is recorded: the rule, WCAG criterion, failing element, and contrast values.
   - "Unique elements": the same rule and selector across views is counted once.
   - axe "needs review" and Alfa "can't tell" items are kept separately from failures.
   - The Pa11y route-link filter, and the patch for an HTML_CodeSniffer bug.
6. **Manual evaluation.**
   - Sample: each author reviews the runs of one assistant. The minimum is one run per assistant and level (9 sites). We review all 27 if time allows. [Say which sites were reviewed.]
   - Calibration: all reviewers review the same site first (Claude Code, Level 1, run-01) and agree on how to judge the checks. Report the agreement on this site.
   - Protocol, in Safari on macOS, in four steps:
     - Keyboard only: skip link, navigation, search and filters, the form, course and table buttons, focus order, visible focus, focus not hidden, the modal (focus in, focus trap, Escape, focus return).
     - VoiceOver: page titles, headings, landmarks, link and button names, text alternatives, table headers, custom control roles and states, current page, form labels, error and status announcements, the dialog name.
     - Visual: reflow at 320 px, zoom at 200%, and no information by color only.
     - Contrast with the Colour Contrast Analyser: focus indicators and field borders (3:1), and up to 3 axe "needs review" contrast items per site.
   - The checklist has 34 checks, each linked to a WCAG 2.2 AA criterion. It goes in the appendix (`checks/manual-checklist.csv`, protocol in `docs/manual-review.md`).
   - Results are recorded as pass, fail, or n/a per site and check, with a note and a screenshot for each failure. A missing feature (for example, no modal) is a fail, not n/a.

## 5. Analysis and Study Barriers [Barriers & Limitations, 10]

This section is about the **process**: what happened, why, what we would change, and what we learned.

- **Copilot and Codex used the same model,** so we replaced Copilot with OpenCode on DeepSeek, and dropped the Copilot runs.
- **The prompt revision after Milestone 1 made the early runs invalid.** All Claude Code and Gemini runs had to be redone. Lesson: research prompting practice before generating anything.
- **Run setup failures:** Claude runs failed on an API key error (401) and a subscription limit (429). The first Claude runs were made by hand outside the runner, without metadata. Lesson: run every condition through the runner from the start.
- **Gemini did not follow the run protocol.** It used the old prompts and ran in Google Antigravity outside the runner, which added a system message. The runs were not redone, so on staff advice we dropped Gemini from the study.
- **A tooling bug was found and fixed.** Pa11y counted single-page-app route links as errors (about 180 false errors). It was found through element-level data, and the first results were archived. A bug in HTML_CodeSniffer also made Pa11y fail on one Gemini site. We patched it in the check image.
- **The manual review scope:** [all 27 sites, or the 9-site minimum and why].
- **Lesson** (end the section with this): what we learned about running AI-generation studies. For example: lock prompts and the run protocol first, use a shared runner and recorded metadata, and look at element-level data instead of totals.

## 6. Limitations [Barriers & Limitations, 10]

This section is about **claims**: what the results can and cannot say, and what still holds.

- **One task:** one app type (course registration) and one visual brief ("colorful"). The results may differ for other UIs.
- **Few runs:** three runs per cell with large variance, so there are no claims of statistical significance.
- **Model snapshot:** the models and versions were current in Oct–Nov 2026, and assistants change quickly.
- **Automated coverage:** the tools see only the initial views and one navigation click, at one viewport size. Lighthouse is not independent of axe-core. Nu checks HTML validity, not a WCAG criterion.
- **Manual review:** [9–27] of 27 sites, one reviewer per site (except the calibration site). The reviewers are students, not accessibility experts, and the screen reader pass used VoiceOver only.
- **Level 3 differs from Level 2 in length as well as specificity,** and its result depends on the quality of our rules file.
- **Three assistants only:** Gemini was dropped, so the results do not cover it.
- **What is still valuable** (end the section with this): the direction and size of the effect between levels, the recurring failure criteria, and the gap between scores and failures.

## 7. Discussion [Results & Discussion, 15]

1. **Answer each RQ directly,** one short subsection each.
   - **RQ1:** default accessibility is decent on the surface but has consistent contrast failures.
   - **RQ2:** a general request is enough for some assistants but not others. Structured rules close the gap.
   - **RQ3:** there is a plateau after Level 2 for two of the assistants.
2. **Implications:**
   - **For developers:** always ask for accessibility, and check the result anyway.
   - **For tool makers (ATAG 2.0):** assistants should apply accessibility by default.
   - **For researchers:** single scores mislead, so report results by criterion.
3. **Connect to related work:**

   - Compare with Doush and Kassem on differences between models.

4. **The role of automated checking:** what can safely be automated in an AI-assisted workflow, and what cannot.
